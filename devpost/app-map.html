ProofPath

A verifier that refuses to accept "done" without proof. This page shows where one real action travels through the code, and where to start when you want to change something.

The pieces

Everything runs in the browser. There is no server, no API key and no network call. Four kinds of pure functions do the work, and the screens only display what they return.

  • Contract (lib/contract/): turns a goal into 1–7 clean requirements, each with an expected outcome and target words.
  • Verifier (lib/verify/): judges each requirement against the evidence linked to it: PROVEN, NOT PROVEN or CONTRADICTED, with a quoted reason.
  • Gaps and card (lib/gap.ts, lib/proofcard.ts): the next test to run for each open requirement, and the Markdown Proof Card at 100%.
  • Store (lib/store.ts): one reducer and one stale flag, saved to the browser's localStorage.

One action: you add evidence and press Verify

Reference route: three stops

A reference route through the current code, not a tour you were walked through. Search for the anchor in quotes to jump to each stop.

  1. The form builds a draft. components/EvidenceForm.tsx, search function submit. It checks the draft with validateDraft (at least one link, a real supersede target) and hands it to the store. "Record this test" pre-fills Input and Action here, never Observed.
  2. The store records it and marks verdicts stale. lib/store.ts, search case "addEvidence", then case "verify". A new item gets the next ID (never reused) and stale: true; Verify calls the verifier and clears stale.
  3. The verifier decides. lib/verify/index.ts, search export function verifyRequirement and export function effectiveStance; then lib/verify/stance.ts, search export function stance. Every item is normalized (lib/text.ts, export function normalize), then screened in a fixed order: injection → hypothetical → vague → contradiction → support. Any contradiction means CONTRADICTED; an agent claim never proves anything on its own. The result appears in components/ProofGraph.tsx, with gaps from lib/gap.ts (buildGaps) and the card from lib/proofcard.ts (buildProofCard).

A practice to reuse

Write every rule's acceptance criteria in both directions, then prove the tests are load-bearing.

When quoted UI text was first exempted from negation, the fix made a real observation pass: R3, where the app shows "The bill can't be negative. Enter 0 or more.". It also opened an evasion: a failure hidden in quotes ("Payment not processed") would pass too. Writing the pass case and the evasion case as tests (tests/quoted-negation.test.ts) pinned the rule to rejects requirements only. Two lines in scripts/mutation.ts then prove that switching either half off fails a test.

On another project: for each acceptance criterion, write one test that a correct result passes and one that the most likely bluff or evasion fails. Then break the code on purpose and check that a test goes red. Otherwise the test isn't protecting anything.

Run it again

npm install then npm run dev and open http://localhost:3000. Checks: npm run verify:all (lint, typecheck, tests, build) and npm run mutation. The live site is toumo45.github.io/proofpathV2.
